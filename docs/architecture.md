# Marble Sort Architecture

## Decision: standalone web game

The first milestone is a standalone Vite application. This keeps gameplay iteration fast and allows the same build to run locally, in a browser, and inside a later Capacitor Android shell.

## Android packaging

The production Vite bundle is packaged in a Capacitor Android application with package ID `com.kemegames.marblesort` and app name `Marble Sort`. `npm run android:sync` rebuilds `dist` and copies it into the native project. `npm run android:apk` also runs Gradle `assembleDebug`; the resulting installable APK is written to `android/app/build/outputs/apk/debug/app-debug.apk`.

Android builds require JDK 21 and an Android SDK. This workstation uses the SDK at `C:\Users\walee\AppData\Local\Android\Sdk`; the generated native project records that path in its untracked `local.properties` file.

## Gameplay state

Tube arrays are stored bottom-to-top. Each tube has a capacity of four. A legal move transfers the contiguous run of the source tube's top color into an empty tube or onto the same color, limited by destination capacity.

Progress, currency, lives and settings are stored in `localStorage` under `marble-sort-state-v1`. The current state schema migrates legacy test balances into the production default opening balance of 500 coins.

## Economy and lives

Coins use one persisted balance across the home HUD, gameplay HUD, daily rewards and level-completion rewards. New installs begin with 500 coins, and each level completion awards 40 coins. The home coin bar routes to the store.

Lives regenerate every 30 minutes up to a maximum of five. Starting a level no longer spends a life. Instead, one life is deducted only when the player reaches a no-moves-left loss state. Regeneration is calculated from the persisted timestamp when the application opens, so it does not require a background timer.

Tapping the lives bar (the home HUD pill or the hearts pill on panel screens) opens a LIVES popup in the gold-frame style: a large heart showing the current live count, a status pill (FULL LIVES when capped), and a per-second "More lives in mm:ss" countdown computed from the persisted regen timestamp — a 1s ticker runs only while the popup is open and re-renders when a life regenerates. Two offers are functional: GET ONE LIFE plays a mock five-second rewarded-ad overlay and then grants one life (the overlay is the placeholder seam for a real rewarded-ad SDK), and REFILL LIVES spends 900 coins to refill to five. Both offers disable to FULL at max lives, and the store's lives card uses the same 900-coin price constant (`LIVES_REFILL_PRICE`).

## Level data

The app exposes 100 level slots. `src/levels.js` is now a board-by-board source of truth rather than a procedural ladder. Visible levels were transcribed from the full-size per-level reference images, preserving the exact left-to-right tube order and the exact bottom-to-top marble order shown in those source boards.

Most levels use two empty tubes, but the imported set also contains special layouts with one empty tube (level 2), no empty tube (level 1), and three empty tubes (levels 23, 46, and 79). The runtime now keeps those exact tube counts instead of forcing everything into one generic pattern.

Some source image slots were blank or missing. Those bridge levels are explicitly tracked in code as inferred boards: `5, 8, 11, 20, 25, 30, 35, 50, 65, 80, 88, 95, 99, 100`. For those entries, the game derives the color set from the nearest neighboring reference boards and generates a deterministic solvable mix that keeps the surrounding tube-count band.

## Interaction rendering

The root screen wrapper no longer replays a fade/scale animation on every render. Gameplay marbles also no longer replay their entry animation when the DOM refreshes for tube selection, modals, or HUD updates. Transfer motion is still animated through the dedicated flying-marble path, but ordinary taps now feel stable instead of producing a brief theme-reload flash.

Tube interaction now responds on `pointerdown` with duplicate-click suppression on the later synthetic `click`, which makes mobile taps feel more immediate than waiting for the browser click phase. When a source tube is already selected, tapping another non-complete non-empty tube now switches selection cleanly instead of showing an invalid-move toast, reducing the sense that a second tap is required before the game recognizes intent.

Because the overlap-friendly board layout makes each tube button roughly 1.8x wider than the horizontal step between tubes, adjacent buttons overlap by about 45% and the later DOM sibling used to capture taps aimed at its neighbor's glass. Tube taps are now resolved by nearest visual center instead of raw button hit: on `pointerdown` (and keyboard-independent clicks) the game measures every tube's bounding box, keeps the ones whose row contains the tap, and selects the tube whose horizontal glass center is closest to the pointer. The `.game-tube:active` CSS transform was removed for the same reason — it visibly moved whichever overlapping button captured the raw press — and the selected tube is raised with `z-index` so its lift renders above neighboring tubes.

Transfer motion was retuned for weight and clarity. Marble flights use per-segment easing — an ease-out launch from the tilted mouth side of the source tube, an accelerating gravity fall into the destination, then an impact squash, a small rebound, and a rest frame — instead of one decelerating curve across the whole path. After playtest feedback that pours still felt slow, flights were tightened to a 400ms base plus 55ms per extra marble with a 55ms stagger, and the post-move resolution delays were shortened to match. Each landing plays a soft high-pitched tick, and the source and target tubes are temporarily raised above their neighbors while they tilt so the pour never renders behind adjacent glass. The post-render marble settle was reduced to a subtle nudge since the flight itself now carries the landing impact.

Completed tubes are now sealed with a round wooden lid (`public/assets/tube-lid-wood.svg`, an original vector asset drawn to match the user-supplied wooden lid reference) instead of the old glass cover and closed-top pair. The falling cover and the persistent sealed cap share the same art and the same box geometry at the tube mouth, so the drop animation lands exactly where the cap stays. The lid falls from above with a gravity ease-in, lands with a squash, takes one small bounce, and settles; the persistent cap is kept hidden from the render pass until the drop lands so the lid never flashes in early.

## Leaderboard and leagues

The leaderboard is a full premium feature opened from the home trophy button (which shows a pulsing red badge whenever season rewards are waiting). The screen matches the approved deep-purple mockup: crown-topped LEADERBOARD banner with laurels, a status row (league chip, live rank, points, info button), a "Season ends in" countdown that ticks while the screen is open, four tabs (Weekly / Stars / Speed / Events), a medal podium for the top three with a crowned first place, clean list cards with movement arrows, and a gold "You" row that pins to the bottom whenever the player is outside the visible list. Rows render 25 at a time with a SHOW MORE control so large boards stay smooth.

All ranking logic lives in `src/leaderboard.js`, a DOM-free module covered by unit tests. Weekly Score = Levels ×100 + Stars ×25 + First-Try Wins ×20 + No-Booster Wins ×15 + Daily Challenge ×100 + Event Points; the game records these per week in `profile.lb` (attempt counts per level detect first-try wins, booster usage is flagged during play, and the fastest booster-free clear each week feeds the Speed board). Six leagues (Bronze → Legend) each run their own 100-player board. Opponents are simulated deterministically from a hash of (season key, league) so a week's competition is stable across sessions, and each bot's score ramps up through the week on its own curve, which also drives the ▲/▼ movement indicators (rank now vs ~6h earlier). The player's movement compares against the rank snapshotted on their last visit.

The weekly boards now blend **real players from Firestore**: every level win (and each leaderboard open) publishes the player's entry to `leaderboards/{season}/{league}/{gameUid}` (name, avatar index, weekly points, stars, levels, best speed), and opening the leaderboard queries the top 100 for the current season/league (`fetchLeaderboardEntries`, ordered by points via Firestore `runQuery` — no composite index needed because season/league are path segments). Real entries replace an equal number of simulated fillers so the board stays at 100, render with their emoji avatars, and rank against both bots and the local player (verified live end-to-end with a seeded player appearing on the podium). Listing is intentionally allowed on this collection only; `players/` remains non-enumerable. The one-minute client cache prevents query spam.

Interstitial ads (mock placeholder, same seam as the rewarded overlay) show at the start of every 2nd level from level 11 (11, 13, 15…, `INTERSTITIAL_START_LEVEL`/`INTERSTITIAL_EVERY`), skipped whenever a tutorial or unlock popup is showing, and tracked as `interstitial_shown`. Boosters now start at **0** and each grants **+2** when its unlock popup is dismissed (`BOOSTER_UNLOCK_GRANT`, shown as a "+2 FREE" chip). The store bundle perk chips wrap to two lines instead of clipping.

The Data Connect (SQL) schema is scaffolded deploy-ready in `dataconnect/` — tables Player, GameSession, LeaderboardEntry, BoosterEvent, Purchase plus a client connector with upsert/insert mutations and leaderboard/profile queries — pending only the Blaze billing upgrade for the Cloud SQL instance.

Seasons are ISO weeks starting Monday 00:00 local. On the first launch of a new week the previous season is finalized: the player's end-of-week rank determines rewards (Top 1 gems + exclusive skin + Champion badge, Top 3 gems + skin, Top 10 gems, Top 100 and top 10% coins) and league movement (top 20% promoted, bottom 20% relegated). The results arrive as a NEW WEEKLY SEASON popup followed by a SEASON RESULTS reward popup with confetti; coins credit the real balance while gems, skins and badges accrue in `profile.lb` as forward-looking cosmetics. Events is a designed empty state until live events ship. The deterministic-bot seams (`generateOpponents`, `buildWeeklyBoard`, etc.) are the exact points where a real backend later substitutes API data, and the entry model already carries the fields needed for friends/regional/global/clan boards, search and profiles.

## Shuffle booster (guaranteed-solvable)

The Shuffle booster rearranges the same marbles in place — it never adds or removes a marble and keeps each tube's exact fill count (empty tubes stay empty). `shuffleTubes` in `src/game-engine.js` draws random permutations of the board's marble multiset into the original per-tube slot counts and accepts the first candidate that is not already solved and is confirmed solvable by `isSolvable` (a bounded canonical-state DFS). The candidate is computed before the booster is charged, so a board that can't be reshuffled (e.g. no empty tubes) shows a "Can't shuffle this board" toast and costs nothing. This replaced an earlier implementation that redistributed marbles into a different tube layout, which could strand marbles and leave the board stuck. Covered by unit tests in `test/game-engine.test.js`.

## Audio and level-complete music

Background music plays continuously during gameplay (no per-SFX ducking — an earlier ducking pass was removed because it made the loop stutter on every tap). Music is only stopped when a level is solved (`musicSuppressed` flag + `pauseMusic()`) so the victory jingle plays clean; it stays off until the player starts a new level (`beginLevel`) or returns home (`setView("home")`).

## Boosters and unlock gating

The three boosters are level-gated: Undo unlocks at level 9, Shuffle at 15, Extra Tube at 18 (`BOOSTER_UNLOCK` in `src/app.js`, LiveOps-configurable). Before its unlock level a booster renders as a dark padlock tile with an "LV n" badge in the gameplay booster bar (`boosterButton()` / `.gameplay-booster.is-locked`); tapping it consumes nothing and shows an "unlocks at level n" toast. Unlocked boosters show their owned count and behave as before. Guards were also added to the undo/shuffle/add-tube paths so a locked booster can never be triggered programmatically. The full booster design (economy, shop, rewards, LiveOps, backend schema, Unity port architecture, analytics, edge cases) is documented in `docs/booster-system.md`.

## Firebase player-data sync

The game syncs player data to the **Marble Sort** Firebase project (`marble-sort-kemegames`, under the Kemegames account). Registered apps: Android `com.kemegames.marblesort` (its `google-services.json` sits in `android/app/`, which also activates the FCM plugin for the Keme push bridge) and a Web app. A Cloud Firestore database (nam5) stores one document per device at `players/{gameUid}` — the same persistent `gameUid` used for Keme support — containing the full profile JSON plus queryable `playerName`/`level`/`coins`/`updatedAt` fields.

`src/cloud-save.js` is a dependency-free Firestore REST client: every `save()` schedules a debounced (4s), best-effort upsert that skips unchanged payloads and swallows offline failures; on boot, a fresh install (not onboarded, nothing unlocked) restores an existing cloud save for its `gameUid` while the splash is still showing. Security rules (`firestore.rules`, deployed via `firebase deploy --only firestore:rules`) allow single-document gets but block listing/enumeration and deletes, and validate write shape and size — verified live (malformed writes and collection listing both return 403). Known limitation: writes are unauthenticated (free-tier Firebase Auth cannot be provisioned via API); once Anonymous Auth is enabled with one click in the console (Authentication → Get started), the rules should be tightened to `request.auth != null` with per-uid mapping.

## Analytics and Data Connect

Google Analytics is enabled on the Firebase project (GA4 property `544219421` under the shared Kemegames Analytics account `397440771`, the same one Marble Blast uses). Two streams exist: the Android app stream (native `firebase-analytics` SDK added to `android/app/build.gradle` for automatic first-open/session events) and a web stream (`G-ZBGDTRZFD7`) used by `src/analytics.js`, a tiny gtag.js loader that sets the persistent `gameUid` as the GA user id and fails silently offline. Tracked gameplay events: `level_start`, `level_complete` (with duration and booster-free flag), `level_failed`, and `booster_used` (with source `inventory`/`coins`, level, and remaining count via `spendBooster`).

Firebase **Data Connect** (SQL/PostgreSQL): the Data Connect service `projects/marble-sort-kemegames/locations/us-central1/services/marble-sort` is created and its API enabled, but the Cloud SQL PostgreSQL instance it requires is blocked on the Spark plan (Cloud SQL needs an attached billing account / Blaze). Once billing is added in the console, the remaining steps are: create the Cloud SQL instance, then define the Data Connect schema + connector (`firebase init dataconnect` scaffolding).

The support surface is implemented in the shared web layer so it works in the browser build and the Capacitor Android APK without duplicating UI. Runtime settings live in `public/keme-support-config.js`, and the full integration notes are documented in `docs/customer-support.md`.

Branding assets are now unified across surfaces: the web shell references `public/assets/favicon.png` and `public/assets/app-icon.png`, and the Android launcher mipmap set is regenerated from the user-supplied square icon so the installed APK uses the same Marble Sort branding on-device.

When `portalBaseUrl` is configured, the game signs the player into Keme's player portal using a persistent local `gameUid`, loads active games, submits tickets, and renders recent ticket history from the Keme API. The Android shell now also includes a native `KemeSupport` Capacitor bridge that initializes on app startup, identifies the guest player before support opens, and prepares Firebase push delegation for the official Keme SDK flow. The remaining native blocker is Keme's missing published Android artifact or a real AAR/JAR delivery.
